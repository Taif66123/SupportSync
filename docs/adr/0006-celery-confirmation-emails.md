# Confirmation email via Celery worker on the Redis broker

Ticket-creation confirmation emails run in a **Celery worker** using **Redis as the broker** (Redis already runs in docker-compose for the M3 bridge — the broker is free infrastructure). The API enqueues a `send_ticket_confirmation` task after its transaction commits — the same commit-gating discipline as notifications: a rolled-back ticket must never produce an email, and a broker outage must never fail the HTTP request (enqueue failures are logged, the ticket still succeeds — fail-open, matching the rest of the Redis usage). Delivery is pluggable: a console backend in dev (the email is logged, no SMTP needed) and real SMTP via env vars when configured. We accept the operational cost of a second moving process (worker + broker) and Celery's configuration surface — chosen by the user over FastAPI BackgroundTasks for the durability and retry semantics a real queue gives; retries are bounded with exponential backoff so a dead SMTP host cannot spin tasks forever. An enqueue-only seam (no broker in unit tests) keeps the suite hermetic; the worker itself is exercised in the live smoke, not in pytest.
