# SupportSync — Milestones

Source: the SupportSync feature list (4 milestones). Status tracked here; decisions live in `docs/adr/`, vocabulary in `CONTEXT.md`.

## Milestone 1 — Login & Support Tickets ✅

**Business**: customer can register and log in; agent can log in; customer creates tickets and sees their own; agent sees the Queue and assigned tickets; agent updates status `open → in_progress → resolved`; customer sees current status.

**Technical**: REST API, JWT auth (15-min access token) with rotating stored refresh tokens (ADR 0003), role-based authorization (Customer / Support Agent / Admin), PostgreSQL, SQLModel, Alembic migrations, pytest.

**Refined during grilling**:
- Three roles; open self-registration for Customers only; Admin creates Agents/Admins.
- Explicit action endpoints (`claim`, `assign`, `resolve`, `reopen`, `close`) — no generic status PATCH. Rules in one declarative table (`tickets/policy.py`).
- Tickets immutable after creation; Priority set by customer, mutable by Agent/Admin; `closed` terminal; Agent/Admin may also close (ADR 0001).
- Admin user management: create, list, role change (last-Admin guard), deactivate/reactivate — never delete (ADR 0004).
- Redis rate limiting deliberately deferred (moved to M3/M4 where Redis is actually introduced).

## Milestone 2 — Real-Time Chat ✅

**Business**: customer and assigned agent chat inside a ticket; messages appear instantly; typing indicator; read receipts; history preserved on reopen.

**Technical**: FastAPI WebSockets, WebSocket authentication, PostgreSQL message storage (new `Message` table shaped by chat needs), typed clients.

**Boundaries already decided**: chat is strictly per-Ticket; participants = ticket Customer + assigned Support Agent; Admins read-only observers; messages sent before assignment are buffered, not delivered, until an Agent claims. Authorization follows the same policy-module pattern as tickets (`chat/policy.py`), it does not extend the tickets policy.

**Built (M2, 94/94 tests green on sqlite + Postgres)**: `messages` table (migration 0002, autogenerated); WS at `GET /api/v1/tickets/{id}/ws?token=<access token>` with pre-accept auth (bad token / invisible ticket → close 1008, no existence leak); protocol `message.send` → `connect.ack{can_send}` / `message.new{message}` / `error{code,message}`, plus `typing.start` → `typing.start{user_id}` broadcast to the room except the typist (ephemeral, never persisted, same send rules — closed chat means no typing); instant delivery via an in-process per-ticket room registry (single-process — Redis fan-out lands in M3); per-frame commit (the WS connection owns its transaction); REST `POST /tickets/{id}/messages` (same rules, for clients without a socket) and paginated `GET /tickets/{id}/messages` (oldest first). Sending on a **closed** ticket → `error.forbidden`, history stays readable. Read receipts: `read.up-to{message_id}` client frame → `read.receipt{user_id,message_id}` broadcast; per-participant markers in `ticket_read_states` (migration 0003), monotonic, silent no-op on repeat/backwards reads; `GET /tickets/{id}/messages/read-states` for ✓✓ state and unread counts; participants only (admins are observers).

## Milestone 3 — Live Notifications — ✅ Complete (Phase A + Phase B)

**Business**: agent notified on new ticket; customer notified on status update and on new message; no refresh needed.

**Technical**: SSE (Server-Sent Events) over long-lived HTTP, server → client push, FastAPI SSE client. **Redis enters the stack here** (pub/sub for fan-out across workers) plus the deferred rate limiting.

**Built (Phase A, 107/107 at the time; Phase A + B = 118/118 green on sqlite + Postgres)**: `GET /api/v1/notifications/stream` (SSE; Bearer header or `?token=`; keep-alive comments; `event:`/`data:` frames of `{type, at, payload}`); typed events `ticket.created` / `ticket.updated` / `message.created`; recipients via declarative `notifications/policy.py` (all active Agents / conversation participants; admins never notified; actor subtracted); emissions **commit-gated** on the request session (`after_commit` publishes, `after_rollback` discards) so a subscriber never hears about unfetchable data; in-process hub fan-out (multi-stream per user); ephemeral by decision — no persistence, no replay.

**Built (Phase B)**: Redis pub/sub bridge (`notifications/bus.py`) — local hub stays this worker's fan-out, pub/sub carries envelopes `{recipients, origin, notification}` **across** workers; emit and stream contracts unchanged from Phase A; origin tag prevents double delivery; self-healing listener (own-worker frames dropped, malformed frames skipped, breaker-gated redial); **shared circuit breaker** in `app/core/redis.py` (one failure → instant fail-open for a 30 s cooldown, then one probe dial — a down Redis costs one dial per cooldown, not one per request); **fixed-window rate limiting** (`app/core/ratelimit.py`, INCR+EXPIRE): register 3/min/IP, login 5/min/IP, refresh 30/min/IP, ticket create 10/min/user, chat send 30/min/user shared by REST + WS frames (`429` with `code: "rate_limited"`); all fail-open by decision. Redis enters `docker-compose` (`redis:7-alpine`); `NOTIFICATIONS_BUS_ENABLED` gates the cross-worker listener (off in tests, on in prod). Chat WS rooms remain single-process by decision — documented constraint, revisit with the M4 frontend.

## Milestone 4 — Background Processing & Finalization

**Business**: confirmation email after ticket creation (async, user doesn't wait); proper error messages; API docs; main flows tested; packaged with Docker.

**Technical**: async/await, FastAPI BackgroundTasks (or a task queue if retries matter), exception handling, pytest coverage of main flows, OpenAPI/Swagger, Docker + docker-compose packaging of backend (and frontend later), CI pipeline (Jenkinsfile).

## Deferred / explicit non-goals

- Cursor-style cursor pagination, departments partitioning the Queue, auto-assignment — revisit only if the domain demands them.
- Hard deletes — never (ADR 0004).
